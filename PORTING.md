# Porting notes

What was verified, what was built, and what is still open. Read this before
trusting anything in `lib/`.

## Verified

These were the open questions before starting; all are now settled with running
code, not assumption.

| Question | Answer |
|---|---|
| Can Ruby verify AMD's RSASSA-PSS/SHA-384 root chain? | **Yes.** Ruby OpenSSL 3.0.13 verifies all six bundled ARK/ASK certificates. |
| Can Ruby produce the 12-byte BLAKE2b ChaChaBox nonce? | **Not out of the box.** OpenSSL's BLAKE2b512 is fixed at 64 bytes, and rbnacl rejects digests under 16 bytes (`BYTES_MIN`). A 12-byte BLAKE2b is not a truncated BLAKE2b-512 — the digest length is mixed into the parameter block. Solved with a bundled pure-Ruby BLAKE2b (`lib/routex/crypto/blake2b.rb`), which matches BouncyCastle exactly at 12 bytes and OpenSSL at 64 across block boundaries. |
| Does `OpenSSL::KDF.hkdf` work with BLAKE2b-512? | **No** — OpenSSL 3's HKDF provider rejects that digest. HMAC-BLAKE2b512 is available, so extract-and-expand is done explicitly. Output matches BouncyCastle's `HKDFBytesGenerator(Blake2bDigest(512))`. |
| Is the whole ChaChaBox construction wire-compatible? | **Yes, byte for byte.** `test/chacha_box_test.rb` seals with a pinned ephemeral key and compares against a ciphertext produced by the upstream primitives on BouncyCastle 1.78.1, and unseals that same ciphertext. |
| Does the attestation path actually verify real hardware evidence? | **Yes, offline.** `test/attestation_verification_test.rb` runs complete VCEK chains and the attestation reports signed under their leaves through the full pipeline: chain, AMD extensions, ECDSA P-384 report signature, platform gates. A genuine Genoa v5 report verifies; genuine Milan, Genoa v3 and Turin reports are rejected for being below the pinned floors; tampering with the signature or the body is caught. |

Golden vectors were generated by compiling the upstream `jvmAndAndroidMain`
crypto primitives against BouncyCastle and running them on fixed inputs.

## Implemented

- **`Crypto`** — SHA-256, BLAKE2b (any length), HKDF-BLAKE2b-512,
  ChaCha20-Poly1305, X25519, Ed25519, raw-scalar-to-DER ECDSA. Pinned to RFC
  vectors and to BouncyCastle.
- **`ChaChaBox`** — seal/unseal. Byte-compatible with upstream.
- **`AttestationReport`** — full SEV-SNP report parser, including the
  Milan/Genoa vs Turin TCB layout split and the pre-v3 CHIP_ID heuristic. Ported
  tests from upstream's `AttestationReportParserTest` pass against the same fixture.
- **`VcekCertificate` / `VcekChain`** — AMD extension readers (product name, the
  five SPL OIDs), path building, signature and constraint validation.
- **`ReportVerifier`** — every platform gate from `ReportVerifier.kt`: signature,
  scalar zero-padding, alias check, debug, migration agent, VMPL, signing-key
  kind, committed firmware and SNP TCB floors, mitigation vectors, per-stepping
  microcode floors, reported-TCB-vs-VCEK match.
- **`SystemVersion`** — Ed25519 signature over the concatenated entry fields,
  with the `Z` → `+00:00` timestamp normalisation upstream applies.
- **`Settlement`** — the full verification order: attestation → ChaChaBox
  binding → system-version signature → measurement match → decrypt.
- **`ClientCore`** — per-ticket settlement caching, header assembly, sealed
  request/response, trace-id unsealing.
- **`TicketIssuer`** — HS256 JWT tickets for all five services.

## Not done

- **The service layer is a sketch.** `Routex::Client` has the right shape and
  paths, but request bodies are built from plain hashes with a naive
  `snake_case` → `camelCase` mapping. Upstream's `models` module is ~3,400 lines
  of typed request/response classes with custom serialisers; that mapping has not
  been reproduced field by field. Expect to correct body shapes against the API
  docs.
- **`ServiceResponse` is a thin wrapper over decoded JSON**, not the typed
  `Response.Dialog` / `Response.Result` hierarchy. `#context` in particular
  guesses at two shapes and needs pinning against real payloads.
- **`RefreshClient`** (non-interactive backend refreshes) is not ported at all.
- **No call against a live endpoint has run.** The settlement *response*
  verification is now covered offline (see above), but the request/response cycle
  against `integration.yaxi.tech` -- and therefore every service call -- is
  unexercised. That still needs credentials.
- **Amount handling.** Upstream preserves decimal scale on the wire
  (`"100.00"` stays `"100.00"`). Ruby's `BigDecimal` can do this but the
  serialisation is not wired up.

## Other official clients

YAXI publishes more ports than the Kotlin one, and they matter for the work left:

| Repository | Language | Note |
|---|---|---|
| `routex-client-kotlin` | Kotlin (KMP) | What this port was written against |
| `routex-client-swift` | Swift | |
| `routex-client-cxx` | C++ | plus `routex-refresh-client-cxx` |
| **`routex-client-lua`** | **Pure Lua** | **The better reference from here on** |
| `routex-react-demo` | TypeScript | worked example of the interrupt loop |
| `moneymoney` | Lua | MoneyMoney extension built on the Lua client |

`routex-client-lua` (MIT) is the closest analogue to this port: a dynamically
typed language with no BouncyCastle and no serialisation framework, so it had to
solve the same problems this port did -- including a pure-language BLAKE2b and
hand-rolled X.509. Its `response.lua` / `result-types.lua` are the model mapping
this port is missing, in a form that translates to Ruby far more directly than
Kotlin's 3,400 lines of typed serialisers. Its `tests/` are the source of the
attestation fixtures used here.

Port the remaining model layer from the Lua client, not from Kotlin.

## The maintenance problem

Two files are pinned security constants that drift with upstream:

- `lib/routex/requirements.rb` — AMD security bulletin floors (currently SB-3023):
  minimum committed firmware, SNP TCB, microcode per CPU stepping, mitigation
  vector bits.
- `lib/routex/yaxi_system_version_keys.rb` — the Ed25519 keys YAXI signs system
  versions with.

When YAXI rolls a new TEE image or AMD publishes a bulletin, upstream updates
these and this port must follow, or every connection fails closed. That ongoing
coupling is a larger long-term cost than the port itself.

**Before investing further, ask YAXI** whether a Ruby client is planned, and
whether they will share the settlement protocol spec and test vectors. The repo
references a `routex-client-swift` with its own `RoutexCrypto` module, so at
least two official ports already exist and the specification is written down
somewhere internal.

## Deliberate deviations

- **No coroutines.** Every upstream `suspend fun` is an ordinary blocking method.
  `Settlement#settle` uses a `Mutex` where upstream uses a coroutine `Mutex`.
- **No `expect`/`actual`.** One target, so the platform split disappears.
- **Comments are kept.** Upstream's security reasoning (why the pre-v3 microcode
  fallback is safe, why absence of a mitigation vector is a failure) is preserved
  in place; losing it would make the gates look arbitrary and invite someone to
  relax them.
- **Errors are flat.** Upstream's sealed error hierarchies collapse to a handful
  of exception classes in `lib/routex/errors.rb`.
