# routex-client-ruby

Ruby port of [`yaxitech/routex-client-kotlin`](https://github.com/yaxitech/routex-client-kotlin),
YAXI's Open Banking client.

**Status: draft / proof of concept.** The cryptographic core and the full
attestation path are implemented and verified -- against the upstream client
byte-for-byte, and against real AMD SEV-SNP evidence offline. The service layer
above them is scaffolded but has never run against a live endpoint. Do not point
this at production. See [PORTING.md](PORTING.md) for what is done, what is not,
and why.

## Why this is not a normal API client

A YAXI service call does not talk to an ordinary HTTP API. It talks to an AMD
SEV-SNP Trusted Execution Environment, and every request and response body is
sealed against that enclave. Before the first call the client must:

1. parse the enclave's SEV-SNP attestation report,
2. validate the VCEK certificate chain up to AMD's root (RSASSA-PSS/SHA-384),
3. verify the report's ECDSA P-384 signature under that VCEK,
4. check the report binds the enclave's ChaChaBox key and matches a YAXI-signed
   launch measurement,
5. and only then derive a session key.

There is no way to skip this and "just call the REST API": without settlement
there is no session id and no server public key.

## Installation

Requires Ruby 3.1+ and OpenSSL 3.0+ (for X25519, ChaCha20-Poly1305 and
BLAKE2b-512). No libsodium, no native extensions.

```ruby
gem "routex-client", github: "cubasepp/routex-client-ruby"
```

## Issuing tickets

Ticket issuance is the piece that is finished and standalone. It runs on your
backend, where the API key secret lives.

```ruby
issuer = Routex::TicketIssuer.new(
  api_key_id: "api-key-2eeba71f-...",
  base64_secret: ENV.fetch("YAXI_API_KEY_SECRET")
)

ticket = issuer.accounts          # => Routex::Ticket
ticket.raw                        # the compact JWT to hand to the client
```

## Calling a service

```ruby
client = Routex::Client.new(base_url: Routex::Client::INTEGRATION_URL)

response = client.accounts(
  ticket,
  credentials: { connection_id: connection_id, user_id: "user" },
  fields: %w[iban currency ownerName]
)

until response.result?
  response =
    case response
    when Routex::Dialog
      # response.context is the dialog's category (Sca, Accounts, ...).
      # The continuation token is response.input_context.
      if response.confirmation?
        client.confirm_accounts(ticket, response.input_context)
      else
        client.respond_accounts(ticket, response.input_context, answer_from_user)
      end
    when Routex::Redirect
      send_user_to(response.url)
      client.confirm_accounts(ticket, response.context)
    when Routex::RedirectHandle
      url = client.register_redirect_uri(ticket, response.handle, "myapp://callback")
      send_user_to(url)
      client.confirm_accounts(ticket, response.context)
    end
end

response.jwt              # authenticated data, signed; verify before acting on it
response.session          # short-lived, pass to the next call to skip re-authentication
response.connection_data  # persist to reuse the consent later
```

A `Dialog` is one of three shapes, and `#input` tells you which:

| Predicate | `#input` | What to do |
|---|---|---|
| `confirmation?` | `context`, `polling_delay_secs` | confirm to proceed (decoupled SCA, or poll after the delay) |
| `selection?` | `options`, `context` | let the user pick one, respond with its `key` |
| `field?` | `type`, `secrecy_level`, `min_length`, `max_length` | collect text, mask it when `masked?` |

Service errors are typed: `Routex::InvalidCredentialsError`,
`Routex::ServiceBlockedError`, `Routex::TicketError` and the rest all descend
from `Routex::ServiceError` and carry `#code`, `#user_message` and `#status`.
Attestation failures descend from `Routex::AttestationError` instead -- they mean
the TEE could not be verified, and are never a normal control-flow condition.

## Running the tests

```
ruby -Ilib -Itest -e 'Dir["test/**/*_test.rb"].each { |f| require File.expand_path(f) }'
```

The suite is offline. It pins the crypto against golden vectors generated by the
upstream Kotlin client running on BouncyCastle, and against the RFC test vectors
for SHA-256, BLAKE2b, HKDF, X25519, ChaCha20-Poly1305 and Ed25519.

It also runs the complete attestation pipeline against real AMD SEV-SNP
material -- genuine VCEK chains and the reports signed under them, for Milan,
Genoa and Turin -- so the verification path is exercised against production
evidence rather than a mock. Provenance is documented in
`test/fixtures/vcek/PROVENANCE.md`.
